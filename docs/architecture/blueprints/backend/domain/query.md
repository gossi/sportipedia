# Query

A named read over the read models. One `new/n` that returns the query — never
the results. `import Ecto.Query` belongs to the body that speaks query macros;
a body delegating to the shared `QueryBuilder` needs none, and the generator
does not write imports it cannot justify.

## Prerequisite

- The [Domain Model](../../../../domain-model/README.md) contains the query, its
  `parameters` and its `result`.
- For the generated (delegating) body: the read model
  ([Read Model](./read-model.md)) — the query names it.

## What the generator does

The module, its `@moduledoc`/`@doc`, the `@spec` returning `Ecto.Query.t()`, and
the `new/…` head for the query's parameters. The **body** depends on what the
model says the query is:

| Query | Body |
| --- | --- |
| a collection read | `QueryBuilder.build(query, <DomainObject>ReadModel)` — complete on generation, with the two aliases it names |
| anything else | the spec's 1%: a stable marker that raises, so an unimplemented query fails loudly instead of returning wrong data |

A collection read is the JSON:API parameter set — `filter`, `sort`, `page`,
`fields` — over the live read-model table, and
`Sportipedia.Support.JSONAPI.QueryBuilder` is the one implementation of that:
partial case-insensitive match per string filter, comma-separated values as an
`IN`, `-`-prefixed descending sorts, `page[number]`/`page[size]` or
`page[limit]`/`page[offset]`, and sparse fieldsets as a `select`. Nothing in the
model is left unimplemented, so the generator ships the working body.

Which reads those are is **declared**, not guessed:
`metadata.annotations."spgen.operation"` on the query, `read` or `collection`.
It is optional — `result.type: array` answers the same question and every model
written before the annotation keeps working — but a declaration that
contradicts the `result` is reported by `mix sp.check`, because the two would
otherwise drive different files. `--template` overrides either.

Not this blueprint: the lookup query behind a unique-field accessor
(`Queries.<DomainObject>BySlug`). That one is complete — it is generated by
`SpGen.Blueprint.LookupQuery` as a dependency of the
[internal API](./internal-api.md) accessor, from the
[unique-slug example](./examples/unique-slug.md).

## Left to you

For a collection read: nothing — and if an earlier run left the marker standing
here, the run reports it as `Outdated` with the body to write, because the merge
never rewrites a line.

For every other query, the `new/…` body, where the generated clause raises
`TODO: implement <query> query (see the feature spec)`:

- filter and sort by what the spec names, within the model's `parameters`;
- return an `Ecto.Query` — `Repo.all`/`Repo.one` is the caller's job
  ([public API](./public-api.md));
- keep the parameter arity the model states;
- own your imports: the generator writes none, and the compiler checks both
  ways — a missing one fails, an unused one warns.

## Tests

In the [operation test](./operation-test.md), under `describe "Query"`: the
generator contributes a placeholder case. Replace it with the behaviour the spec
states — a collection's body is generated, but its behaviour (filtering,
sorting, pagination over seeded fixtures) is only proven by a test.
